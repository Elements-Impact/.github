# Org-wide Copilot rules

Applies to all repositories under this organization. Repository-level files named `.github/copilot-instructions.md` may extend or override specifics while respecting the org security and licensing rules below.

## Scope & precedence

- Use Copilot for code, docs, and tests that follow repo conventions.
- Org rules here take precedence for security, privacy, and licensing.
- Repos may add additional constraints but must not weaken org rules.

## Security & privacy

- Never propose, paste, or invent secrets/keys/tokens. Assume config comes from env/secret stores.
- Do not access or modify credentials folders or tenant configs.
- No `eval`, remote code execution, or unsanitized HTML/SQL. Follow secure defaults.
- Treat PII and business-sensitive data as confidential. Use realistic placeholders in examples.

## Licensing & provenance

- Do not include code that is clearly copied from sources with incompatible licenses.
- Prefer small, well-maintained, permissive-license libs. Avoid adding new runtime deps unless essential.

## Coding standards

- Match each repo’s language, framework, and folder patterns.
- Prefer minimal diffs, strict types, tests for behavior changes, and reuse of shared utilities.
- Avoid unnecessary abstractions and logging noise. Fix root causes, not symptoms.

## Documentation & Collaboration

- Write clear, comprehensive documentation for all public APIs and complex logic
- Use descriptive variable and function names that convey intent
- Include meaningful commit messages following conventional commit standards
- Add comments for business logic, not obvious code
- Consider non-native English speakers in documentation

## Performance & DX

- Keep heavy work off critical paths; avoid blocking the UI.
- Use existing linting, formatting, and testing workflows. Add/adjust tests when changing behavior.

## Do not modify

- Build artifacts, lockfiles, or CI config unless requested.
- Generated or vendor folders, secrets files, or environment files.

## Suggested ignore patterns for prompts/edits

- node_modules, build outputs, caches, lockfiles
- .env\* and secrets
- Generated code and large binary assets

## Git & Version Control

- Use conventional commit format: `type(scope): description`
- Types: feat, fix, docs, style, refactor, test, chore, ci, perf
- Keep commits atomic and focused
- Write meaningful commit messages that explain the "why"
- Reference issues and pull requests where applicable

## When in doubt

- Ask for clarification, reference repo docs/README, and align with maintainers’ guidelines.
